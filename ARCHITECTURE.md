# Архитектура

Слоистая архитектура с чётким разделением: Router (aiogram-хендлеры) →
Service (бизнес-логика) → Repository (SQLAlchemy-запросы) → Database.
Роутер никогда не обращается к репозиторию напрямую - только через
сервис; сервис не знает про Telegram-типы. Сборка объектов - через
DI-контейнер (`dependency_injector`), не вручную по хендлерам.

Игровой дизайн (что и почему) описан в `BATTLE_DESIGN.md`/
`BATTLE_ENGINE.md`/`ECONOMY.md`/`REGENERATION.md` - этот файл только про
то, где что лежит и как слои связаны друг с другом.

## Структура репозитория

```text
.
├── src/
│   ├── bot/              # Весь Telegram-бот (см. ниже)
│   ├── config.py         # pydantic-settings, переменные окружения (см. "Три конфига")
│   ├── database/
│   │   └── models/       # SQLAlchemy-модели (общие для бота и миграций)
│   ├── assets/           # Гифки/видео/шрифты для рассылок и медиа-команд
│   └── userbot_parser/   # Отдельный сервис-парсер поверх Pyrogram
│       └── src/          # (свой config.py/main.py, свой .env - независим от бота)
├── migrations/           # Alembic (versions/ - и схема, и data-миграции seed-строк)
├── tests/
│   ├── conftest.py       # Реальный Postgres в Docker per-test (docker-py, не sqlite)
│   ├── unit/             # Плоско, без вложенных папок, одна сессия на тест
│   └── integration/      # Настоящая многосессионная конкурентность (гонки за
│                         # баланс и т.п.) + межсервисные сценарии - меньше по
│                         # объёму, но не дублирует unit/, а проверяет другое
├── dialogs.json          # Весь пользовательский текст ботов-ответов (см. ниже)
└── *.md                  # Дизайн-доки (см. корень репозитория)
```

## `src/bot/` - разбор по каталогам

- **`routers/`** - только приём апдейтов и вызов сервисов, без бизнес-логики.
  - `common/` - команды, не завязанные на расу гуля (профиль, баланс,
    переводы, вордли, старт/хелп).
  - `ghoul_routers/` - вся механика гуля (голод/статы/кагуне/бои).
    `routes.py` внутри - `include_ghoul_routers()`, регистрирует их все в
    один под-`Router`. `duel/` - отдельный под-пакет (FSM дуэли: инвайт,
    таймауты в фоне, разыгрывание боя, финализация исхода - см.
    `BATTLE_ENGINE.md`).
  - `creator_routers/` - админ-команды создателя бота (бан, сброс
    прогресса, выдача кагуне, левел-ап руками, сброс кулдаунов и т.д.).
    Единственный вход под этот namespace - `CreatorMiddleware`
    (`settings.ADMIN_IDS`), проверка не размазана по хендлерам.
  - `moderator_routers/` - настройки приветствия/правил чата, доступ
    через `ModeratorMiddleware`.
  - `chat_member_update_routers/` - события входа/выхода из чата
    (`SyncEntitiesService`, обновление `Chat`/`User`).
- **`services/`** - вся бизнес-логика, ничего не знает про
  `aiogram.types`. `Base` (`services/base.py`) - общий конструктор с
  4 базовыми репозиториями (`user`/`ghoul`/`cooldown`/`chat`), большинство
  сервисов от него наследуются, чтобы не тащить одни и те же зависимости
  в каждый `__init__` заново.
  - `battle_engine/` - боевой движок:
    - `core/` - **чистый домен, без БД и без Telegram** (`Fighter`,
      `Battle`, все формулы урона/уклонения/сжатия статов). Специально
      изолирован, чтобы будущие боевые фичи (рейды, "стенка на стенку")
      строились поверх него без переписывания.
    - `battle_service.py`/`mob.py`/`text_generator.py` - мост между
      `Ghoul`/БД и чистым `core/` (собирает `Fighter` из `Ghoul`, рендерит
      результат боя в `RichMessage`/текст).
  - `admin/` - сервисы под `creator_routers/` (бан, ресет, статы, поиск
    игрока, рассылка) - намеренно отдельно от "игровых" сервисов.
  - `ghoul_game/`, `wordle_game/`, `video/` - самостоятельные мини-игры/
    утилиты, у каждой свой под-пакет вместо одного raw-файла.
  - Заметные одиночные файлы: `ghoul.py` (статы/голод/смерть/поедание),
    `level_up.py`, `battle_record.py` (история боёв + `ActiveBattle`-лок
    против одновременных боёв), `cooldown.py`, `notification_ticker.py`
    (фоновый тикер уведомлений о голоде/здоровье), `media.py` (медиа-
    коллекции гифок из БД, не путать с `bot/config.py` ниже).
- **`repositories/`** - только SQLAlchemy-запросы, один на модель/группу
  моделей. Атомарные операции (`try_claim`, `atomic_update` с условным
  `WHERE ... RETURNING`) - устоявшийся паттерн вместо "прочитать-потом-
  записать" везде, где есть риск гонки (кулдауны, локи боёв, FSM дуэли).
- **`middlewares/`** - `database_middleware.py` (сессия на весь хендлер),
  `ghoul_middleware.py` (блокирует мёртвых гулей), `creator_middleware.py`/
  `moderator_middleware.py`/`ban_middleware.py` (проверки доступа),
  `sync_entity_middleware.py` (апдейт `User`/`Chat` на каждое сообщение).
- **`exceptions/`** - типизированные исключения по доменам
  (`battle.py`, `transfer.py`, `chat.py`, ...) - роутеры ловят их точечно
  вместо голого `except Exception`.
- **`filters/`**, **`utils/`**, **`types/`** - вспомогательные модули
  (кастомные aiogram-фильтры, чистые функции расчётов, enum-подобные
  типы вроде `KaguneType`/`Race`).
- **Три разных "конфига", не перепутать**:
  - `src/config.py` - `pydantic-settings`, переменные окружения
    (`BOT_TOKEN`, `POSTGRES_*`, ...), инстанцируется на импорте.
  - `src/bot/config.py` - пути до папок с ассетами (гифки/видео),
    переменная называется `game_config` - легко спутать со следующим.
  - `src/bot/game_configs.py` - **балансные игровые константы**
    (`BATTLE_CONFIG`, `MOB_CONFIG`, `EAT_HUMAN_CONFIG`, `DUEL_CONFIG`,
    ...) - сюда смотреть в первую очередь при вопросе "а где число X".
- **`containers.py`** - DI-граф целиком: репозиторий → сервис → роутер
  через `Provide[Container.xxx]` + `@inject`. Новый СЕРВИС требует
  правки здесь (новый provider); `__main__.py` (список `packages=[...]`
  для wiring) трогать нужно, только если завёлся НОВЫЙ пакет роутеров -
  новый файл в уже перечисленном пакете подхватывается автоматически
  (проверено: `creator_routers/cooldown_admin.py` заработал без единой
  правки в `__main__.py`).

## Текст и данные вне кода

- **`dialogs.json`** - весь пользовательский текст (кроме rich-сообщений,
  которые собираются программно из `InputRichBlock*`) - `DialogService`
  читает его лениво и перечитывает при изменении mtime, деплоить бота
  заново ради правки текста не нужно.
- **`migrations/versions/`** - не только DDL: часть миграций - чистый
  seed/data-апдейт (типы кулдаунов, их длительность) без изменения схемы.

## Поток запроса

1. Апдейт от Telegram → `DatabaseMiddleware` (открывает сессию на всю
   обработку) → остальные middlewares (регистрация/доступ/бан) → роутер.
2. Роутер валидирует вход, вызывает 1+ сервисов (через DI).
3. Сервис вызывает репозитории, применяет бизнес-правила, может вызвать
   другие сервисы (например `BattleService` дёргает `GhoulService` за
   кагуне-статами).
4. Ответ - `message.answer()`/`message.answer_rich()` обратно в Telegram;
   `DatabaseMiddleware` коммитит и закрывает сессию по выходу из хендлера.

**Важный нюанс**: фоновые задачи (`asyncio.create_task` - таймауты дуэли,
`NotificationTicker`) переживают закрытие сессии хендлера, который их
запустил - им нельзя передавать DI-инжектированные сервисы из этого
хендлера, они открывают СВОЮ сессию через `session_factory` и сами
собирают нужные сервисы (см. `duel/background.py`).

## Тесты

`tests/conftest.py` поднимает настоящий одноразовый Postgres в Docker на
каждый прогон (`Base.metadata.create_all`, без Alembic) - тесты никогда
не гоняют миграции, поэтому seed-данные (типы кулдаунов и т.п.) в тестах
заводятся руками через фикстуры, а не ждутся из миграций. Каждая новая
миграция при этом всё равно вручную проверяется (`upgrade`+`downgrade`)
против отдельного одноразового контейнера - см. историю коммитов
`migrations/`.

## Развёртывание

`docker-compose.yml`: `postgres` → `migrations` (`alembic upgrade head`,
разовый сервис) → `bot` (ждёт оба через `depends_on: condition:
service_healthy/service_completed_successfully`) - миграции накатываются
сами при `docker compose up`, руками катить не нужно. `pgadmin` - для
ручной инспекции БД, `db_backup`/`rclone_backup` - ежедневный дамп +
синк в облако.
