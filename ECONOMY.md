# Экономика CheSton/RC - разбор на атомы

Как и `BATTLE_ENGINE.md` для боя - отдельный файл, чтобы держать в голове
не всё разом. Повод завести именно сейчас: пытались удешевить прокачку
`max_health` (см. `BATTLE_ENGINE.md`/симуляции боя - health должен быть
~2.5x от боевых статов, иначе бой решается за 1 раунд), и выяснилось, что
это нельзя сделать в отрыве от всего остального - сколько вообще игрок
зарабатывает CheSton, и на что эти деньги тратятся.

## Часть 0 - зачем это вообще

Три связанных, но разных куска, которые нельзя решать по отдельности:

1. Сколько CheSton реально зарабатывает игрок за день (часть 1).
2. По какой цене он тратит их на прокачку статов, в частности health
   (часть 2).
3. Сколько CheSton/RC будет давать бой с мобом - источник, которого
   физически ещё не существует (часть 3).

Пока не понятен пункт 1 - бессмысленно трогать 2 и 3 (число "нужно 2.5x
дешевле" ничего не значит без понимания, сколько вообще есть денег).

## Часть 1 - Источники CheSton (аудит)

Все источники ниже платят в `User.balance` (CheSton) - не путать с RC
(`Ghoul.rc_money`, отдельная валюта, см. часть 4).

| Источник | Команда | Кулдаун | Награда | Дневной потолок (теоретический) |
|---|---|---|---|---|
| Щёлк | "щелк"/"щёлк" | 10 мин (`SNAP`, `duration=600`) | 500-1500 | 144 × 500-1500 = 72,000-216,000 |
| Кофе | "пить кофе" | 30 мин (`COFFEE`, `duration=1800`), доступен только после `snap_count >= 100` | 5000-9000 | 48 × 5000-9000 = 240,000-432,000 |
| Вордли | "вордли"/"вротли"/`/wordle` | ✅ намеренно нет (см. ниже) | 7000-14000 за победу | не ограничено движком - только скоростью игрока |
| /quiz | `/quiz` | ✅ намеренно нет пока (см. ниже) | 5000-10000 | не ограничено движком, сейчас нерабочий по другой причине (см. ниже) |
| Депнуть (лотерея) | "депнуть" | нет (это не фарм) | ставка × коэффициент (1.8x-10x, шанс 10-28%) | не источник дохода - азартная игра, у части исходов отрицательный результат, считать наравне с фармом нельзя |

**✅ Пересмотрено - изначально записано как "пробел", но это осознанный дизайн:**

- **Вордли без кулдауна - НЕ баг.** `wordle_router.py` живёт в
  `routers/common/`, не в `routers/ghoul_routers/` - это чатовая
  развлекательная игра для всех, а не гульская механика, кулдаун "на
  гуля" или "на всех" для неё бессмысленен по конструкции. Реальный
  тормоз для живого игрока - архаичный список слов (намеренно), из-за
  которого победа занимает реальное время; кулдаун наказал бы честного
  игрока не меньше скрипта. Скрипт-фарм (слова и код открыты на GitHub)
  - это отдельная проблема **автоматизации**, решается будущей системой
  модерации/бана за скрипты, а не игровым кулдауном - живой игрок фармить
  сколько угодно ДОЛЖЕН мочь, это часть замысла. Награда специально мала
  относительно поздней экономики (нужны десятки-сотни побед) - осознанный
  "лёгкий подъём для новичков", не серьёзный поздний рычаг. Вордли - не
  последняя такая чатовая игра, награда в них по замыслу поддерживает
  вовлечённость ("дофамин"), не баланс статов.
- **`/quiz` тоже без кулдауна - тоже осознанно, но по другому механизму.**
  Тип вопросов виден в README библиотеки `ghoul_quiz` - случайный
  "проходимец" без знания лора вынужден гуглить каждый ответ (барьер по
  УСИЛИЮ/времени на вопрос, не по времени ожидания), а настоящий знаток
  лора отвечает мгновенно - это специально устроенная награда за реальное
  знание лора проекта, а не дыра. 🔲 На будущее (не срочно) - конечный пул
  вопросов теоретически можно один раз пройти с гуглом и превратить в
  шпаргалку, тогда барьер станет разовым, а не постоянным - плюс уже
  запланирован лимит игр в сутки, тоже не срочно.

✅ **Реальная проблема с `/quiz` - только техническая, не про фарм.**
Команда сейчас **нерабочая** - зависит от внешнего пакета
`ghoul_quiz.GhoulQuizAPI` с отдельным `GHOUL_QUIZ_API_KEY` (см.
`src/bot/services/ghoul_quiz.py`). Это и есть единственное, что
действительно требует починки (или явного отключения команды, пока не
починено) - независимо от вопроса лимитов.

## Часть 2 - Цена прокачки статов (как есть сейчас)

`game_configs.py`:

```python
def stat_cap_for_level(level: int, stat_key: str = "") -> int:
    return int(level * 100 * STAT_CAP_MULTIPLIER.get(stat_key, 1.0))

STAT_CAP_MULTIPLIER = {"max_health": 2.5}

class StatUpgradeConfig:
    stat_price_multiplier = {"max_health": 0.4}

    def price(self, cur_stat: int, count: int = 1, stat_key: str = "") -> int:
        base_total = count * 1500
        scaling_total = int(sum((cur_stat + i) ** 1.35 for i in range(count)))
        return int((base_total + scaling_total) * self.stat_price_multiplier.get(stat_key, 1.0))
```

✅ Потолок `max_health` поднят до 2.5x относительно остальных 4 статов -
число взято прямо из симуляций боя (`scripts/battle_log_all_kagune.py`),
не придумано.

🔲 **Множитель цены 0.4x - ПРОВИЗОРНЫЙ, найден неверным.** Из-за степенной
части формулы (`** 1.35`) суммарный CheSton "с нуля до потолка" растёт
быстрее, чем сам потолок - плоский множитель не может дать точный паритет
на всех уровнях сразу. Посчитано, какой множитель РЕАЛЬНО нужен для
паритета на разных уровнях:

| уровень | нужный множитель для паритета |
|---|---|
| 1 | 0.30 |
| 5 | 0.17 |
| 10 | 0.14 |
| 20 | 0.13 |
| 50 | 0.12 |

С текущими 0.4x health до потолка на деле **дороже** обычного стата (на
5 уровне - примерно в 2.4 раза), не так же. Автор решил не чинить это
прямо сейчас изолированно - см. часть 0, сначала нужен аудит доходов
(часть 1) и понимание источника наград за бой (часть 3), и только потом
пересчитывать саму кривую (возможно, не плоским множителем, а другой
формой - см. открытый вопрос ниже).

🔲 Открытый вопрос: чинить через два числа (степень+множитель) вместо
одного, или явно принять, что паритет не идеален и достаточно "примерно
для типичного уровня 5-10" - решение отложено до понимания доходов.

## Часть 3 - RC-экономика (для контекста, отдельная валюта)

RC (`Ghoul.rc_money`) - НЕ CheSton, отдельная валюта, тратится на новые
типы кагуне/какуджу (`KAGUNE_CONFIG`), а не на прокачку `STATS`. Основной
источник сейчас - награда за левел-ап (`LEVEL_UP_CONFIG.rc_reward`,
5-20 RC × уровень) и будущее поедание побеждённых гулей (`BATTLE_ENGINE.md`
4.3, формула ещё не задана). Здесь не разбирается подробно - фиксируется
только чтобы не путать с CheSton при проектировании наград за бой ниже.

## Часть 4 - Награда за бой с мобом (не существует, самое важное новое)

❓ **Настоящий пробел, не просто открытый вопрос** - сейчас в
`BATTLE_DESIGN.md`/`BATTLE_ENGINE.md` про фарм мобов сказано только про
RC ("формула ÷5, статы моба случайны 0.5x-2x, малый шанс 1-2 RC" - 4.5).
Про CheSton там нет ни слова - если бой должен ещё и кормить прокачку
статов (в частности health), этот источник нужно спроектировать с нуля.

Автор сформулировал целевое ощущение (не формулу): после 1-2 побед над
мобом игрок должен суметь прокачать хотя бы 1 стат примерно на 50% от
шага прогресса - то есть награда должна быть **привязана к уровню**
(как `LEVEL_UP_CONFIG`, не фиксированное число).

🔲 Не решено: точная формула (флэт от уровня? доля от цены следующего
шага прокачки того же уровня, чтобы само определение "50%" было честным,
не приблизительным?), и делится ли эта награда с RC-наградой того же боя
или это независимые начисления.
